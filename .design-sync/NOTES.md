# design-sync notes — waterman

Repo-specific gotchas for syncing this repo to claude.ai/design. Read this
before re-running the sync.

## What this repo is, from the converter's point of view

`waterman` is a **Next.js application**, not a published component package.
There is no `dist/`, no `.d.ts` tree, no Storybook, and components are `.js`
files containing JSX. Three consequences drive most of the setup below:

- **The converter's discovery only globs `.tsx`/`.jsx`.** Our components are
  `.js`, so they are invisible to it. Every component is therefore pinned
  explicitly in `cfg.componentSrcMap` (72 entries, generated — see below).
- **esbuild only applies the JSX loader by file extension**, so `.js` files with
  JSX fail to parse. `lib/bundle.mjs` defines the output contract and must not
  be forked, so `.design-sync/build.mjs` pre-compiles the components to a real
  ESM entry and the converter consumes *that* as the package's "dist".
- **There are no shipped prop types.** Contracts are generated into
  `cfg.dtsPropsFor` from the destructured signatures + JSDoc (see below).

## Always run the prep build first

```sh
node .design-sync/build.mjs      # this is cfg.buildCmd
```

It produces the three converter inputs, and MUST run before `package-build.mjs`
on every sync:

1. `.design-sync/entry.js` — barrel re-exporting all 72 components
   (regenerated by `make-entry.mjs`; add a component and it appears here)
2. `.design-sync/.cache/dist/index.js` — that barrel compiled to ESM, JSX
   compiled away, bare package imports left external
3. `.design-sync/.cache/tailwind.css` — `app/globals.css` compiled by Tailwind
   (`cfg.cssEntry`)

Then the converter run for this repo is:

```sh
node .ds-sync/package-build.mjs --config .design-sync/config.json \
  --node-modules ./node_modules --entry ./.design-sync/.cache/dist/index.js \
  --out ./ds-bundle
```

The `--entry` flag is **required** — there is no discoverable dist entry.

## Gotchas that cost real debugging time

- **`process` is not defined in a browser bundle.** `components/ConvexProvider.js`
  constructs a Convex client at *module scope* from `process.env.NEXT_PUBLIC_CONVEX_URL`
  (Next inlines these at build time; a plain IIFE has no `process`). Unfixed, the
  whole bundle throws at import and **every one of the 72 previews renders blank**.
  Fixed by `.design-sync/env-shim.js`, imported first by the barrel.
  **The shim must stay a SEPARATE module** — `build.mjs` marks it `external` on
  purpose. ESM evaluates a module's imports before its own body, so if the shim
  is inlined into the entry it runs *after* every component has already read
  `process`, and the error comes straight back. This is subtle; do not "simplify"
  it away.
- **Env values point at `https://ds-preview.invalid`** deliberately: no real
  environment values ship in the bundle and no preview issues live network calls.
  Consequence: every Convex `useQuery` stays `undefined` forever, so components
  that fetch their own data cannot render statically — they need data passed as
  props, or they are honestly empty. See "Re-sync risks".
- **Next.js routing is stubbed.** `next/navigation` and `next/link` are aliased
  to inert stand-ins in `.design-sync/stubs/`. The real modules throw
  "invariant expected app router to be mounted" outside a Next app and blanked
  9 components. The stubs also keep the bundle portable, which is correct for a
  design system consumed outside Next.
- **`components/ui` was being grouped as "general".** The converter treats `ui`
  as a generic container directory, which dumped all 24 primitives into one
  meaningless group. `.design-sync/overrides/source-kit.mjs` is a one-line fork
  removing `ui` from `GENERIC_DIR` (declared in `cfg.libOverrides`). Its sibling
  imports are repointed at `../../.ds-sync/lib/` because siblings do not exist
  under `overrides/`.
- **`cfg.guidelinesGlob` is deliberately `[]`.** The default globs picked up
  `docs/README.md`, which is a **repository security/architecture audit** —
  it names open write boundaries and vulnerabilities. That must not be inlined
  into the design agent as "design guidelines". Leave it empty unless real
  design guidance is added to the repo.

## Prop contracts

`node .design-sync/make-dts-props.mjs` regenerates `cfg.dtsPropsFor` from the
destructured parameter lists + JSDoc `@param` tags. Note `tsc --allowJs
--declaration` is NOT usable here: with a single destructured object parameter
it binds the first `@param` to the whole object and emits a wrong signature
(e.g. `Button(props: "primary"|"secondary"|…)`).

The generator resolves a type in this order: JSDoc → icon usage (`<Icon/>` ⇒
`React.ComponentType`, `{icon}` ⇒ `React.ReactNode`) → variant union recovered
from the component's own style lookup table → default value → prop-name
convention. Hand edits in `config.json` win; the merge only fills gaps.

Four components (BottomNav, GlobalNavigation, Loader, UserMenu) take no props
at all — an empty contract there is correct, not a miss.

## Fonts

The app loads Playfair Display / Inter / Courier Prime from
`fonts.googleapis.com`. The bundle **self-hosts them instead**
(`node .design-sync/fetch-fonts.mjs` → `.design-sync/fonts/`, wired via
`cfg.extraFonts`), and `build.mjs` strips the remote `@import` from the synced
stylesheet so the two declarations cannot compete. `app/globals.css` is not
modified. Verified: all three families load with **zero external requests**.
All three are SIL Open Font License, so redistribution is permitted.

## Render check

No playwright browser download is needed — playwright drives the Chrome that
puppeteer already cached:

```sh
export DS_CHROMIUM_PATH="$HOME/.cache/puppeteer/chrome/mac_arm-143.0.7499.40/chrome-mac-arm64/Google Chrome for Testing.app/Contents/MacOS/Google Chrome for Testing"
```

If that Chrome version is ever pruned, re-point `DS_CHROMIUM_PATH` at whatever
is under `~/.cache/puppeteer/chrome/` (or install playwright's own chromium).

## Re-sync risks — what can silently go stale

- **The puppeteer Chrome path is version-pinned** (`mac_arm-143.0.7499.40`) in
  the export above. A puppeteer upgrade changes it and the render check fails
  with "Executable doesn't exist". Re-read the cache dir, do not assume.
- **Fixture data lives inside the preview `.tsx` files.** Previews for the
  data-driven components (forecast, tide, journal, webcam) hand-build objects
  matching what each component destructures. If those component signatures
  change, the preview still compiles but renders wrong or empty — the render
  check catches blank, not *stale-but-plausible*. Re-read any preview whose
  component changed shape.
- **`.design-sync/stubs/` mirror a Next.js API surface.** If components start
  using a `next/navigation` export the stub does not define (e.g. a new hook),
  it will be `undefined` at runtime rather than a clear error. Add it to the
  stub when that happens.
- **Convex-fetching components can never render real data** by design (see the
  `.invalid` note). Any component that looks empty in the DS pane should be
  checked against that list before being treated as a regression.
- **`make-entry.mjs` decides the component list by regex** over export
  statements. An unusual export form (re-export barrels, `export const X = memo(...)`
  wrapped oddly) may be missed silently — the count printed by the build is the
  thing to watch (72 today).
- The repo's `npm run build` / `npm test` / `npm run lint` are broken
  independently of this sync (documented in `docs/README.md`); do not treat
  them as a signal about the design-sync pipeline.

## Re-syncing: the whole thing in one command

```sh
# 0. fresh clone only: install converter deps + recreate the fork symlink
#    (cp the staged scripts first — a stale .ds-sync/ runs an old converter)
SB=<skill-base-dir>/design-sync
mkdir -p .ds-sync && cp -r "$SB"/package-*.mjs "$SB"/resync.mjs "$SB"/lib "$SB"/storybook .ds-sync/
echo '{"name":"ds-sync-deps","private":true}' > .ds-sync/package.json
(cd .ds-sync && npm i esbuild ts-morph @types/react typescript && PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1 npm i playwright)
ln -sfn ../.ds-sync/node_modules .design-sync/node_modules

# 1. prep build (cfg.buildCmd) — ALWAYS, it produces the converter's inputs
node .design-sync/build.mjs

# 2. fetch the project's anchor so unchanged components skip re-verification
#    (projectId is in config.json; save it here)
#    → .design-sync/.cache/remote-sync.json

# 3. the driver: build → diff → validate → capture, one verdict JSON
export DS_CHROMIUM_PATH="$HOME/.cache/puppeteer/chrome/<version>/chrome-mac-arm64/Google Chrome for Testing.app/Contents/MacOS/Google Chrome for Testing"
node .ds-sync/resync.mjs --config .design-sync/config.json --node-modules ./node_modules \
  --entry ./.design-sync/.cache/dist/index.js --out ./ds-bundle \
  --remote .design-sync/.cache/remote-sync.json
```

Then grade anything in `verification.pendingGrade` from the fresh sheets, check
validate's warn lines against "Known render warns" below, and upload per the
skill's §5 if `upload.any` is true.

**This sync's baseline (2026-08-03):** 72 components, 69 authored previews all
graded `good`, 3 deliberate floor cards, render check 72/72 clean, validate
exits 0 with no warnings. A re-sync that reports materially worse than that has
regressed — do not just accept it.

## Preview-authoring gotchas (learned the hard way)

- **Tailwind never scanned the previews — fixed.** `tailwind.sync.js` used to
  list `'./.design-sync/previews/**'` as a content glob. Tailwind globs with
  fast-glob, which **skips dot-directories**, so that glob matched nothing and
  every utility class a preview introduced silently produced no CSS — cells
  rendered unstyled or collapsed. It now passes the preview sources as `raw`
  content entries instead. If you touch that config, verify a class that only
  a preview uses actually lands in `.design-sync/.cache/tailwind.css`.
  Note: `preview-rebuild.mjs` still does not recompile CSS, so a preview that
  introduces a brand-new class needs a full `node .design-sync/build.mjs`
  (+ `package-build.mjs`) before that class exists. Several wave-1 previews use
  inline `style={{}}` for layout glue as a workaround from before the fix —
  harmless, no need to unpick.
- **`position: fixed` overlays collapse to a zero-height root.** `.ds-cell` and
  `.ds-single` in the generated card HTML carry `transform: translateZ(0)`,
  which makes them the containing block for fixed descendants. In `?story=`
  capture mode the story mounts into `#r0.ds-single`, whose height is its
  in-flow content — and an overlay contributes none, so `fixed inset-0`
  resolves to a zero-height box and the overlay is cropped. Fix from inside the
  preview: wrap the story in an explicit `minHeight` stage div (see
  `previews/Modal.tsx`). `cfg.overrides.<Name>.cardMode` alone does NOT fix
  this — capture always uses the `?story=` / `.ds-single` path. Affects every
  overlay: Modal, ScoreModal, WebcamModal, WebcamFullscreen, MobileMenu,
  OnboardingModal, TvMode.
- **framer-motion enter animations race the screenshot.** Capture shoots right
  after `networkidle` + settle; on a warm page a component that animates
  `opacity 0 → 1` with a delay (FilterBar's filter row) can be photographed at
  opacity 0. If a cell looks empty but a cold load shows content, this is why.
- **Card overrides applied:** `TideChart: {cardMode:"column"}` (its chart is
  wider than a grid cell) and `Modal: {cardMode:"single", primaryStory:
  "ScoreBreakdown"}` (overlay escapes the grid). Both came from
  `[GRID_OVERFLOW]` warns naming the exact remedy.

## Capture-harness facts (wave 2)

- **Screenshots are a fixed 900×700 viewport, `fullPage: false`.** Anything
  taller than ~650px is silently cropped, and an overlay stage taller than
  ~676px gets clipped — but a stage *shorter* than the panel lets it spill past
  its own scrim. ScoreModal took two iterations to settle at 640–660px.
- **900×700 is `orientation: landscape` and matches `md:`.** Two components hid
  themselves because of it: `BottomNav` is `md:hidden` (so it was
  `display:none`, nothing to do with its fixed positioning), and
  `WebcamFullscreen`'s entire metadata layer is `landscape:hidden`. The latter
  is not fixable from a preview — it now has a portrait card viewport override.
- **CSS animations land on random frames.** `Loader` animates `height: 15px → 0`
  on a 1s alternate loop and photographed blank; the preview pins it with
  `.loader{animation-play-state:paused}`. Same family as the framer-motion issue
  below.
- **framer-motion can spoil a render without emptying it.** MobileMenu captured
  with the sheet fully at rest but *no* `bg-black/40` scrim — the 200ms opacity
  tween had not started while the slower spring had settled. A cell can be
  plausible-looking and still wrong; pin the animated property with a local
  `<style>` rule (see `previews/FilterBar.tsx`, `previews/MobileMenu.tsx`).
- **Don't give webcam fixtures a fake stream URL.** With no URL, `getStreamUrl()`
  returns null and the card flips straight to its genuine CAM OFFLINE
  placeholder. A `.invalid` m3u8 instead makes hls.js treat DNS failure as
  recoverable and loop `startLoad()` for the full 12s timeout, making
  `networkidle` slow and non-deterministic.
- **`Toast` auto-dismisses after `duration` ms (default 3000)** — previews must
  pass `duration={0}`, which skips the timer and makes the cell capture-stable.

## Card overrides in use, and why

`cfg.overrides` is now 16 entries. Almost all were prescribed verbatim by a
`[GRID_OVERFLOW]` warn, which names the exact remedy — read the warn, apply what
it says, batch them into ONE targeted `preview-rebuild.mjs` run:

- `cardMode: "column"` (renders wider than a grid cell): `TideChart`,
  `DaySection`, `ForecastSlot`, `ViewToggle`.
- `cardMode: "single"` + `primaryStory` (fixed/portal content escapes the grid):
  `Modal`, `Toast`, `ToastProvider`, `ScoreModal`, `WebcamModal`, `BottomNav`,
  `GlobalNavigation`, `MobileMenu`, `OnboardingFooter`, `OnboardingModal`,
  `TvMode`.
- `WebcamFullscreen`: `cardMode: "single"` + `viewport: "480x860"` — the
  portrait viewport described above.

Note `single` shows only the one named story, so the other cells stop appearing
on the card. That is the accepted trade for overlays: they cannot be presented
in a grid at all.

## Hooks are exported into the bundle

`make-entry.mjs` also exports `use*` hooks (`useAuth`, `useUser`, `useToast`)
into `window.Waterman`, not just components. They are part of the system's real
API — a design built on `AuthProvider`/`ToastProvider` needs them — and they are
deliberately kept OUT of `componentSrcMap`, since only PascalCase names are
components and a hook must never become a card.

## Components that cannot render in a preview (deliberate floor cards)

- **`LiveWindRow`, `LiveWindIndicator`** — no data props; both `fetch(
  '/api/live-wind/<stationId>')` themselves and return `null` on loading, error,
  or a reading older than 60 min. That route does not exist outside the app, so
  they render nothing. Authored previews were **deliberately removed**: the only
  thing a card could show is surrounding scaffolding, which would teach the
  design agent that the component renders content it cannot. They ship
  functional in the bundle with docs in `.design-sync/docs/` explaining the
  dependency. Do not "fix" this by stubbing fetch — the stub would make the card
  lie about what the component does in a real design.
- **`UserMenu`** — `if (!user) return null`, and `useAuth().user` is permanently
  null in the harness: there is no session token, and seeding one would not help
  because `AuthProvider` validates it via `ConvexHttpClient.query` against the
  `.invalid` host. Same treatment and same reasoning as the pair above; docs in
  `.design-sync/docs/UserMenu.md`. (If a future sync wants auth-gated surfaces
  to render, the one central fix is seeding a token AND stubbing
  `ConvexHttpClient.prototype.query` with a fixture user — that would unblock
  the header user slot, profile and journal surfaces together.)
- **`LocationPicker`** — builds its own `ConvexHttpClient` and fetches
  `api.spots.list`; against `.invalid` the query rejects, so the spot list is
  always empty ("No spots found"). Its chrome and its custom-location branch DO
  render, so it has a real card; the populated list is simply unreachable.

Statically unreachable *states* (documented, deliberately not faked): the
`MagicLinkSent` code-entry and onboarding branches; `OnboardingFlow` steps 2–4
(step 3 also fetches spots); `EmailLoginForm` loading/error; `OnboardingModal`
steps 2–4 — its only static axis is `isDismissible`. `EmptyState` has **no
message prop** at all (copy is hard-coded "NO CONDITIONS"), so a copy sweep is
not authorable without a component change.

## Component facts worth keeping (from preview authoring)

- **Wind direction is offset by 180°.** `lib/utils.getDisplayWindDirection(deg)`
  returns `getCardinalDirection(deg + 180)`. `ConditionLine`, `DirectionIndicator`
  and `ForecastComparison` all apply it, so a stored bearing of `315` prints
  `SE`, while `Arrow direction={315}` rotates the glyph to point NW. Fixtures
  must use `stored = displayed − 180`, and never hand-write a cardinal that
  contradicts the rendered one.
- `DurationDisplay` takes `minutes` (a number) — not ms, not an object.
- `SessionCard` needs a full `entry`: `_id`, `sport`, `spotName` or
  `customLocation`, `sessionDate`, `durationMinutes`, `rating`, optional
  `sessionNotes` / `hasForecastData`. A year suffix appears only for
  non-current-year dates.
- `TideChart({tides})` needs ≥2 `{time, height, timeStr}` entries to draw.
  Build tide timestamps with the local-time `new Date(y,m,d,h,min)` constructor,
  not epoch literals — `formatTideTime` uses `getHours()` and epoch literals
  shift with the capture browser's timezone.
- `ScoreDisplay` and `ScorePill` return `null` below score 60 unless `showAll`;
  `ScoreCard` tiers break at 90/75/60, so a tinting sweep needs four scores.
- `FilterBar` has no `expanded` prop — it reads `waterman_filters_expanded`
  from localStorage, defaulting to `window.innerWidth >= 768`.
- Forecast fixtures follow `lib/slots.js` `enrichSlots`: `slot.score.value`,
  `spotsData[spotId]`, `spotsMap[spotId].sports`, `tidesBySpot[spotId].tides`.
  Day fixtures must sit on the capture's pinned clock date or `isToday()`
  suppresses the live affordances.
- `DaySection`'s header is `sticky md:top-[50px]`, expecting the app's 50px
  global nav; in a card it needs ~32px top padding or it rides over the first
  spot name.

## Bugs found in the app's own components (NOT fixed — out of scope for a sync)

Surfaced while building previews; worth a real fix in the app:

1. `TideSection.js:39` and `TideTable.js:35` guard `tide.height !== null` then
   call `.toFixed(1)` — an `undefined` height throws. Should be `!= null`.
2. `TideChart.js` calls `useRef`/`useState`/`useEffect` (lines 34–47) *after* an
   early `return null` (lines 6–8) — conditional hooks, a rules-of-hooks
   violation that survives only because `tides` never flips empty↔non-empty
   within one mount.
3. `TideSection.js:10` does `slots.forEach` unguarded — crashes on `undefined`.
4. `ForecastComparison` is a misnomer: it does not compare logged vs forecast
   conditions, it only lists `forecastSlots`, and its `sport` prop is accepted
   but never read.
5. `ForecastComparison`'s slot cards use literal `bg-white` instead of
   `bg-newsprint`, so they read cooler than the rest of the design language.
6. `components/admin/ToastProvider.js` **exposes no context**: it defines
   `showToast`/`removeToast` but never publishes them, while the separately
   exported `useToast()` keeps its *own* state and its *own* `ToastContainer`.
   A component wrapped by `ToastProvider` therefore cannot make it show a toast.
7. `components/calendar/CalendarView.js` **duplicates spots**:
   `groupedSpots = [...wingfoilSpots, ...kitesurfingSpots, ...surfingSpots]`
   puts one spot in several buckets and the flat-entry loop then emits
   `sportData.length` rows *per bucket* — a spot scoring ≥60 for both wingfoil
   and kitesurfing renders 4 near-identical rows. Reproduced in capture; the
   fixtures now give each spot one qualifying sport per day so the card does not
   teach the bug.

Also worth knowing (not a bug): `Toast` and `SpotConfigForm` are admin surfaces
that do **not** use the newsprint/ink token set (`bg-green-500`, `bg-red-500`,
plain `border-ink/30` inputs). That is the real code — but it means they are not
representative of the design language, and the design agent should not imitate
them for user-facing UI.

## Known render warns

Legitimate warns triaged during the preview waves — a warn NOT in this list is
new and should be looked at:

- `[GRID_OVERFLOW]` on `TideChart` and `Modal` — remedied via `cfg.overrides`
  (see above). `column` cards cannot re-flag `wide`; `single` cards are exempt.
- `TideDisplay`'s trend branch is icon-only by design, so that cell is sparse —
  the honest render, not a broken one.
- `RatingInput`'s `disabled` state only changes cursor/hover affordances, so it
  is visually identical to the enabled state in a static screenshot.
